# Lore Spec (Step 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish the Lore v1 specification (`spec/SPEC.md`) with JSON Schemas, an error registry, inline conformance examples, a checker that keeps them valid, and the agent paragraph.

**Architecture:** The spec is one Markdown document with conformance examples inline, CommonMark style. Machine-readable parts live beside it in `spec/` (schemas, error registry, agent paragraph). A small TypeScript checker extracts the examples and validates their structure, their expected outputs against the schemas, and the spec's coverage. It never parses Lore itself: that is the reference parser's job in step 2, which will run these same examples.

**Tech Stack:** Bun (runtime and test runner), TypeScript (strict), `ajv` (JSON Schema 2020-12), `yaml` (eemeli/yaml v2, dev only, for schema tests), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-25-lore-spec-design.md` (the design). Every normative statement written into `spec/SPEC.md` comes from it; where this plan names a value, it is copied from there.

## Global Constraints

- No tool-specific terms anywhere in `spec/` or the README: no product names, no internal paths. Examples use a fictional `acme/shop` repo (`apps/web/src/checkout/...`).
- Normative language is RFC 2119 / RFC 8174 (MUST, SHOULD, MAY in capitals).
- Structured blocks are YAML 1.2 core schema; JSON accepted; no anchors, aliases or custom tags; duplicate keys are errors.
- Id pattern `^[a-z][a-z0-9-]*$`; category pattern `^[a-z][a-z0-9_]*$`.
- The nine fixed categories, exactly: `functional_correctness`, `test_coverage`, `security`, `performance`, `accessibility`, `observability`, `backwards_compatibility`, `documentation`, `code_style`.
- Severity values: `blocking`, `advisory` (default `advisory`).
- `.loreconfig` keys: `lore` (const `1`), `root` (boolean), `repo` (`<host>/<path>`), `categories`, `disable`.
- `<when>` keys: `addedContains`, `addedMatches`, `changed`, `unchanged`.
- `<check>` languages: `regex` (default), `ast-grep`.
- Files are UTF-8 with LF line endings; the checker rejects CR in `spec/SPEC.md`.
- License: spec text CC-BY-4.0 (`LICENSE-CC-BY-4.0`), schemas, examples and code MIT (`LICENSE`). Both files exist already.

## Review Focus

1. **Lore prose that itself contains fences.** An example whose Lore input has a ```` ``` ```` fenced block (the "closing tag inside a fence" rule) must extract intact. Pinned in Task 3 (`extracts an example whose input contains a triple-backtick fence`).
2. **Intentionally invalid inputs.** Error examples deliberately contain broken YAML or tags; the checker must not reject them. Pinned in Task 4 (`never parses example inputs`).
3. **RFC words inside examples.** "MUST" appearing inside an example block or a code span must not count toward section coverage. Pinned in Task 4 (`ignores RFC words inside examples and code`).
4. **CRLF in the spec.** A Windows editor saving `SPEC.md` silently changes example bytes. Pinned in Task 4 (`rejects CR characters`).
5. **An eligibility example missing its diff**, or a parse example carrying one. Pinned in Task 4 (`requires a diff exactly for eligibility examples`).

## Example syntax (decided here; the design left it to the builder)

An example is a fenced block opened with six backticks and the info string `example <kind>`, where kind is `parse` or `eligibility`. Six backticks let Lore inputs contain ordinary three-backtick fences. Inside, sections start with `=== `:

```````
``````example eligibility
=== .lore/rules.lore
<rule id="currency-from-settings">
<when>
addedContains: ["'USD'"]
</when>
Display text never hard-codes a currency code.
</rule>
=== diff
M apps/web/src/checkout/Price.tsx
+12 const label = 'USD'
=== expect
{ "eligible": ["currency-from-settings"], "hits": [], "excluded": [], "warnings": [] }
``````
```````

- `=== <path>`: an input file at that path in the governed repo.
- `=== external:<path>`: an input file in an external Lore folder the tool was given (path relative to that folder's own repo root).
- `=== remote` (eligibility only, optional): one line, the governed repo's remote URL, for `repo` matching. Without it, external folders match only if their `repo` is `github.com/acme/shop`.
- `=== diff` (eligibility only): lines `A <path>`, `M <path>`, `D <path>`, `R <old> -> <new>`; each may be followed by added lines `+<line number> <text>` belonging to that file's new path.
- `=== expect`: JSON, validated against `document-model.schema.json` (parse) or `eligibility.schema.json` (eligibility).
- An optional `requires: ast-grep` line directly after the opening fence marks an example only tools supporting that check language must pass.
- Examples are numbered by the checker in document order. Their section is the nearest preceding `##` or `###` heading.
- **What the governed repo contains:** exactly the `=== <path>` input files plus every path the diff adds, modifies or renames to. A changed file's full content may be given as an input file; when it is, each `+<n> <text>` line must equal line `n` of that input (the checker enforces this). `ast-grep` examples and "missing `src` target" examples rely on this.

This syntax is itself written into SPEC.md (Task 5, `## Conformance examples`), so implementers in other languages can run the suite without this plan.

## Expected-output conventions (every `=== expect` follows these)

- **Paths.** `Entry.file` and `Diagnostic.file` are the input path exactly as written after `=== `, with `external:` kept for external files. Globs in `Entry.scopes` are resolved to paths from the governed repo's root (external files through their `repo` mapping).
- **`Diagnostic.line`** is 1-based within that file: the offending line for YAML problems (counted in the file, not the block); otherwise the opening tag line of the element at fault; for problems with no single line (`top-level-text` uses its first stray line), 1. A `.loreconfig` problem uses the offending key's line, else 1. `Diagnostic.entry` is the entry's id when the problem is inside an entry with a readable id, else null.
- **`prose`** is every line after the last child element up to the closing tag, with leading and trailing blank lines removed and the rest byte-exact, joined with `\n`. **`summary`** is the first paragraph of `prose` (up to the first blank line), its lines joined with a single space. A context with no body has `prose: ""` and `summary: ""`.
- **`hits[].line`** is the `+<n>` line number from the diff; `text` is that line's text.

## Error names: which one fires

Specific names win. The generic shape errors (`invalid-defaults`, `invalid-scope`, `invalid-when`, `invalid-meta`) fire only for a shape failure no specific name covers, such as a wrong type (`files: "src/**"`) or `<meta>` holding a scalar.

| Problem | Name |
|---|---|
| YAML that doesn't parse | `invalid-yaml` |
| Duplicate key | `duplicate-key` |
| Anchor, alias or custom tag | `yaml-feature-not-allowed` |
| Unknown `<when>` key | `unknown-condition` (not `invalid-when`) |
| `<when>` with no keys | `empty-when` |
| Malformed glob (`src/[a`, `{a,b`) | `invalid-glob` |
| `..` in a glob | `glob-escapes-base` |
| Leading `/` outside `changed`/`unchanged` | `leading-slash` |
| `files: []` | `empty-files` |
| Undeclared category in `<defaults>` | `unknown-category`, reported at file level, whole file excluded |
| Unknown severity in `<defaults>` | `invalid-defaults` |

The `..` rule applies to every glob, including `changed` and `unchanged`.

## Behaviors the design didn't pin (decided here, flagged in the handoff)

- A `.loreconfig` with any error is ignored as a whole and reported (`invalid-loreconfig`); entries that relied on its categories then fail with `unknown-category`, entry by entry.
- `repo-inside-repo` and `nested-repo` exclude every Lore file at or below the offending `.loreconfig`.
- `ast-grep` is pinned to the latest ast-grep release at the time Task 7 runs; SPEC.md names the exact version.
- `<context>` takes `id`, `src` and `disabled`. `category` or `severity` on a context is `unknown-attribute`. Context entries have `category: null` and `severity: null`, and `missing-category` never fires for them.
- `<!-- -->` comments are recognized only at the top level. Inside an entry, a comment line ends the children and starts the prose (it is a Markdown comment in the prose).
- CI runs `bun run check` from Task 1 on, so it is red until Tasks 4 and 5 land. That is expected on this branch; don't work around it.

### Task 4: Checker and CLI

**Files:**
- Create: `tools/check/check.ts`, `tools/check/cli.ts`
- Test: `tests/check.test.ts`

**Interfaces:**
- Consumes: `extractExamples` (Task 3); schemas (Tasks 1-2); `spec/errors.json`.
- Produces:

```ts
export interface Problem { rule: string; line: number; message: string }
export interface RegistryEntry { name: string; kind: "error" | "warning"; description: string }
export type SchemaName = "defaults" | "scope" | "when" | "meta" | "loreconfig" | "document-model" | "eligibility";
export type SchemaSet = Record<SchemaName, object>;
export function checkSpec(input: { markdown: string; registry: RegistryEntry[]; schemas: SchemaSet }): Problem[];
```

`cli.ts` reads `spec/SPEC.md`, `spec/errors.json` and `spec/schemas/*`, prints each problem as `SPEC.md:<line> <rule>: <message>`, prints `N examples, M sections covered` on success, exits 1 on any problem.

Checker rules (each a `rule` name in `Problem`):
- `cr`: the spec contains a CR character.
- `kind`: an example's kind is not `parse` or `eligibility`.
- `inputs`: an example has no input file.
- `diff`: an eligibility example has no diff, or a parse example has a diff or a remote.
- `diff-syntax`: a diff line isn't `A|M|D <path>`, `R <old> -> <new>`, or `+<n> <text>` after a file line.
- `expect`: missing, not JSON, or fails its kind's schema.
- `sorted`: an eligibility `eligible` list isn't sorted.
- `unknown-name`: an expect names an error or warning not in the registry.
- `unknown-id`: an eligibility `eligible` or `hits[].rule` id doesn't appear as `id="<id>"` in the example's inputs.
- `diff-agrees`: a `+<n> <text>` line disagrees with line `n` of an input file at the same path.
- `coverage`: a `##`/`###` section whose own prose (excluding examples, fenced code and inline code) contains an RFC 2119 keyword has no example. Exempt sections (and their subsections): `Introduction`, `Conventions`, `Conformance examples`, `Document model`, `Errors and warnings`, `For agents (non-normative)`, `Adopting Lore (non-normative)`.
- `untested-name`: a registry name appears in no example's expect.
- `registry-table`: the first Markdown table after the `## Errors and warnings` heading has columns `Name | Kind | Description`, name cells in backticks (`` `name` ``), rows in the same order as `spec/errors.json`; any difference in names, kinds or order is a problem.

Problems with no single location (`untested-name`, `registry-table`) report line 1.

The checker never parses example inputs.

- [ ] **Step 1: Write the failing tests**, one per rule plus: `never parses example inputs` (an example with broken YAML input and a matching expect yields no problems), `ignores RFC words inside examples and code`, `rejects CR characters`, `requires a diff exactly for eligibility examples`, `checks + lines against a matching input file` (diff-agrees), `exempt sections need no example`, `a clean spec yields no problems`. Build small Markdown fixtures inline.
- [ ] **Step 2: Run** `bun test tests/check.test.ts`. Expected: FAIL.
- [ ] **Step 3: Implement `checkSpec` and `cli.ts`.** `untested-name` and `registry-table` only fire once `spec/SPEC.md` contains the heading `## Errors and warnings` (Task 9), so Tasks 5-8 can land green.
